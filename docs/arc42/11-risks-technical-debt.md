# 11. Risks and Technical Debt

| # | Risk / Debt | Impact | Notes |
|---|---|---|---|
| 1 | **`renderToCanvas` creates a new `WebGLRenderer` on every call** | GPU resource leak under repeated calls (e.g. a UI re-rendering on every frame-index change). | Documented in `render.ts` as `TODO(post-v1)`: cache the `WebGLRenderer` as a private field instead. `renderFrame` (without `ToCanvas`) exists as a workaround — it lets a consumer manage their own renderer — but `renderToCanvas` itself does not yet do this. |
| 2 | **`dispose()` is narrower than the original design promised** | A consumer relying on `dispose(scene)` alone to fully release GPU resources will still leak the `WebGLRenderer` instance and any label-sprite textures. | Only mesh/line geometry and material in the *given* scene are disposed; the renderer instance and textures are untouched. Needs either a wider `dispose()` or clearer documentation of what it does and doesn't cover. |
| 3 | **Carried-ball offset assumes right-handed players** | Ball placement is visually wrong for a left-handed player, which OCF has no way to express yet. | Documented `TODO(post-v1)` in `compose-frame.ts`: the offset is a fixed forward/right-hand direction because the schema carries no handedness tag on entities. Blocked on a schema change in `spec`, not fixable renderer-side alone. |
| 4 | **Named-position catalog can drift from `ocf-validator`'s canonical list** | A position name that validates successfully (validator's catalog has it) can still fail at render time with "Unknown named position" if the renderer's local `src/court/named-positions.ts` hasn't been kept in sync — this is exactly the bug class that prompted this documentation effort. | No automated cross-repo check exists today; the two catalogs are independently maintained files in two repos. A shared source of truth (e.g. published from `spec` or `validator`) would remove this class of bug permanently rather than relying on manual vigilance. |
| 5 | **Design doc vs. real code drift** | `docs/superpowers/specs/2026-07-20-ocf-renderer-threejs-design.md` describes an async, container-first API (`Promise<RenderResult>`, `constructor(container, opts)`) that does not match the shipped synchronous, document-first API. A reader trusting the design doc over the source will misintegrate. | This arc42 set is grounded in the real `src/` as of 2026-08, not the design doc; see [ADR-03](09-architecture-decisions.md). The design doc itself has not been corrected or marked superseded on this point. |
| 6 | **No headless/server-side rendering path** | A consumer needing a static image export (e.g. "download this play as PNG" on a server, without a real browser) has no supported path — `THREE.WebGLRenderer` requires a real WebGL context. | Explicit constraint (see [Constraints §2](02-architecture-constraints.md)), not an oversight, but worth tracking if such a use case becomes a real requirement (would likely mean a headless-GL or SSR-canvas dependency). |
| 7 | **CDN staleness risk, mitigated but not eliminated** | The original production bug ("Unknown named position") was ultimately caused by the docs-site playground pinning a `cdn.jsdelivr.net/gh/...` git-commit reference that never advanced past a stale build. | Fixed by switching the playground to `cdn.jsdelivr.net/npm/...`, pinned to an explicit published version (see [Deployment View §7.4](07-deployment-view.md)) — this removes the "silently never updates" failure mode, but the playground's pinned version must still be bumped deliberately after each renderer release, which is a manual step, not automated. |
| 8 | **`ci.yml` does not run the full test suite** | `npm run test:visual` (Playwright pixel-diff) and `npm run test:browser` (bundle-shape verification) are not part of `ci.yml`'s steps — only `npm test` (vitest) runs in CI. A regression only these two catch could merge to `main` undetected. | Worth adding to `ci.yml`, weighed against Playwright's heavier CI runtime/browser-install cost. |
